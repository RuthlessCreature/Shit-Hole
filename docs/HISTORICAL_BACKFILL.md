# 逻辑B历史日线回填：2020-01-01起

## 真实边界

- 请求区间：2020-01-01 至 2026-11-20（最后一个已完整收市的交易周末尾）；2020-01-01是休市日，预计最早有效日为2020-01-02。
- 通过369交易日历API取得实际开市日期，禁止按周一到周五近似生成交易日。日历原始响应及SHA-256保存在私有R2。
- 每个交易日最多一次全市场 `day_kline?date=...` 请求；每条正常记录完整保存在R2（原始JSON、标准化JSONL、审计manifest）。缺失/ST/停牌/零量均不作为研究过滤条件。
- 历史日线以R2为全量事实库。超过当前日期45天的历史窗口**不再逐码写D1**：D1单库最大10GB，不能把整个七年市场灌爆。D1仍逐日记录抓取量、来源、状态及R2路径。最近45自然日的回填以及持续每日增量可同时写D1逐码明细。
- 历史数据源是单一369，并未与交易所独立证券主表对账；因此每个批次仍然最多 `PROVISIONAL` 或 `PARTIAL`，绝不称为 VERIFIED。2020年的A股数量远低于2026年，固定5000只异常基线自然会标成PARTIAL，**不能将其直接解释为真正缺失**。

## 2026-11-23 全量模式历史阶段（现已升级为Queue）

- 首批三个交易日 `2020-01-02`、`2020-01-03`、`2020-01-06` 已全部归档，分别5346、5351、5350条，共**16047条**，无抓取失败。原有3次试抓保护达到 `PILOT_COMPLETE`；用户随后**明确要求取消试抓次数限制、对剩余全部交易日连续回填**。
- 新定义：生产`backfill_control.attempt_limit=0`表示**无限制的完整日期队列模式**，不是执行0次。`state='RUNNING',enabled=1`恢复任务。普通上游500等短暂失败同一交易日最多自动重试3次，不静默跳过；最终有无法成功日期则标`FINISHED_WITH_GAPS`，不虚报全量完成。401/403/429仍然停机并审计。
- 曾短暂将历史Cron改为`*/5 * * * *`，每5分钟处理1个交易日。此定时等待方案已按用户最新要求废止，改为下述Queue接力。

## 连续接力模式（用户2026-11-23最新确认）

用户进一步明确要求**不得每5分钟等待下一交易日；必须当日数据抓取、R2归档与D1审计成功后立即开始下一交易日**。

- 将历史回填由Cron替换为独立的 `shit-hole-history-backfill` Cloudflare Queue；同一个Worker同时作为生产者和消费者。单条消息、单消费者并发。每次只完成1个交易日并等待持久化提交，然后立刻投递下一条，不在日期之间设固定间隔。
- `backfill_days` 和 `backfill_control` 仍是持久队列游标；Cloudflare Queue的至少一次投递可能重复，因此仍通过D1占位锁和日状态确保每个日期只处理一次成功归档，不能仅依赖消息顺序。
- 为避免免费接口日额500次被短时间打满，每个北京时间自然日最多计入450条369行情调用（包括正常每日行情），达到预算就把下一条消息延迟到下一个北京时间自然日00:10。服务商实际重置时间/剩余额度仍可能不同，以429为准。
- 429不反复冲击上游：将当前日期保留为待抓并在下一自然日恢复；401/403鉴权/禁止访问则暂停并公开报错。普通网络或服务端错误同日期最多3次重试，不能静默漏日。
- 历史回填无需5分钟Cron；保留的Cron只负责正常工作日北京时间16:20增量采集。Queue执行速度由供应商真实响应、D1/R2持久化与Cloudflare投递延迟决定，不再宣称固定N天内必然补齐。

## 旧Cron自动回填方案（已废止，留作审计）

- 新增 `cloudflare/migrations/0002_backfill.sql`，表为 `backfill_control` 和 `backfill_days`；先迁移，再发布新版Worker。
- 曾用每5分钟独立历史Cron（`*/5 * * * *`，UTC），每次处理1个交易日；最新方案已替换为Queue，现有北京时间16:20当日增量Cron仍保留。
- 最初的3日试抓已于16:45完成；用户随后明确要求全量执行。生产将设置`attempt_limit=0`，不再由试抓次数上限中途暂停。
- 如果遇到401/403/429，当前日记为`BLOCKED`、回填立即暂停；其它异常记为失败，保留原因，不绕封锁、不无限重试。
- 本次全量恢复只调整 `backfill_control.attempt_limit/enabled/state`，保留原有交易日及完成批次，不从头重复抓；阶段性监控服务商额度和实际存储量。
- `backfill_days.status='STORED_UNVERIFIED'`意为原始/标准化日线已落私有R2，**不代表数据覆盖完全，更不等于有估值证据**。

## 云端验收SQL

用已授权Cloudflare插件在本项目D1中执行（无需本地常驻服务）：

```sql
SELECT state,enabled,start_date,end_date,calendar_rows,attempts,attempt_limit,
       last_error,calendar_loaded_at FROM backfill_control WHERE id=1;

SELECT trade_date,status,attempts,last_run_id,last_error
FROM backfill_days ORDER BY trade_date LIMIT 10;

SELECT trade_date,status,normalized_rows,raw_key,normalized_key,manifest_key,audit_json,error
FROM market_runs WHERE trade_date < '2026-01-01' ORDER BY trade_date LIMIT 5;
```

核实R2中的 `provider.json`、`normalized.jsonl` 与 `manifest.json` 实体存在、内容可解析、数量与数据库审计一致，并抽样跨源比对价格与交易日。
